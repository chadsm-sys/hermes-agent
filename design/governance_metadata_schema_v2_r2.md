## 2. Versioning note

The `olympus-governance-metadata/v2` profile has never been published, implemented,
fixture-tested, or certified. The v2→v3 semantic-immutability rule in
`design/backward_compatibility.md` governs profiles from their first certified
publication onward; it does not freeze a design that has produced zero records.
R2 therefore redefines the v2 profile before first publication. To make R2 records
distinguishable by construction, all digest domain separators carry the `/v2r2` suffix
(see `design/digest_domain_specification.md`); a record built under the reviewed
pre-R2 design can never collide with an R2 record.

## 4. Amended field definitions

### 4.1 Field 2 `event_ref` — fixture namespace (resolves P2-4)

- **Allowed values:** `^(live|fixture)-[a-f0-9]{24}$`
- `live-` references exactly one event in the immutable certified v1 stream.
- `fixture-` references exactly one entry in a declared synthetic fixture manifest and
  must never resolve to, or be joined against, the live v1 stream.
- A certification run declares exactly one `corpus_class` (`live` or `fixture`) in its
  replay payload. A `live` run rejects every `fixture-` reference; a `fixture` run
  rejects every `live-` reference. Mixed-namespace runs are invalid and fail closed.
- No fixture is generated by this design; the namespace is defined so that future
  fixture work cannot masquerade as live-bound records.

### 4.2 Field 6 `policy_conflict_indicator` — all-string enum (resolves P2-1)

- **Type:** enum string (JSON booleans are no longer valid for this field)
- **Allowed values:** `no_conflict`, `conflict`, `unknown`
- This closes open question 8: the record contains strings only, in every field, which
  simplifies canonicalization (§5) and strict validation. All prior analysis of the
  tri-state semantics carries over with `true→conflict`, `false→no_conflict`.

### 4.3 Field 15 `uncertainty_reason` — derivation status (dispositions P3-1)

`uncertainty_reason` is declared a **derived consistency-check field**: it is a
deterministic function of fields 5–12 and 14 under the normative priority order
(schema, authority, policy, contract, evidence, missing metadata, other). It is
retained despite redundancy because reviewers consume it directly and because a
mismatch between the embedded value and the recomputed value is itself a defect
signal. Consumers must recompute it; a mismatch makes the record ineligible for a
definitive correctness label (`validation class: invalid_derived_field`).

### 4.4 Field 18 `advisory_output_digest` — new (resolves P1)

- **Type:** opaque string
- **Allowed values:** `^adv-[a-f0-9]{64}$`
- **Source:** computed by the certification assembler (independent of Olympus) at
  advisory-freeze time, per `design/digest_domain_specification.md`
- **Native/derived:** derived integrity binding
- **Justification:** binds the frozen advisory outputs (fields 13–15) to this record's
  `event_ref` and `provenance_identifier`, making post-freeze substitution of any
  advisory value detectable by hash recomputation alone — without re-executing the
  advisory engine (P1 requirement).
- **Privacy impact:** none beyond existing hash-correlation controls; digest over
  values already present in the record.
- **Security impact:** integrity label only; not a capability, not authentication.
  Trusted-origin authenticity is addressed by `design/provenance_authenticity_plan.md`.
- **Abuse analysis:** an attacker who rewrites fields 13–15 must also rewrite this
  digest; the forgery is then caught against the externally anchored run manifest
  (ordered advisory-digest list and `advisory_set_digest`), not against the record
  alone. Validators recompute; they never trust the embedded value.
- **Data minimization:** one digest.
- **Replay impact:** input to `advisory_set_digest`, which is an input to
  `replay_identifier`; excluded from `provenance_identifier` to preserve
  anti-circularity.
- **Certification benefit:** cheap tamper-evidence for the adjudication target.

### 4.5 Fields 16 and 17 — digest domains made exact (resolves P1)

The prose definitions of `replay_identifier` and `provenance_identifier` in the
reviewed design are replaced by the byte-exact definitions in
`design/digest_domain_specification.md`. Summary of the corrections:

- The ambiguous term "v2 metadata-set digest" is retired. `replay_identifier` binds the
  ordered **fact-set digest** (over per-record `provenance_identifier` values) and the
  ordered **advisory-set digest** (over per-record `advisory_output_digest` values), so
  advisory outputs are integrity-bound at run level.
- `replay_identifier` (field 16) appears in no digest input, including its own.
- `provenance_identifier` (field 17) covers fields 1–12 plus pinned source and
  taxonomy digests, and continues to exclude fields 13–15, 16, and 18 — Olympus
  outputs still cannot influence fact provenance (anti-circularity preserved).

## 5. Canonicalization (normative summary)

Full rules in `design/digest_domain_specification.md`. In brief: UTF-8 JSON objects;
keys sorted lexicographically by Unicode code point; no insignificant whitespace;
every value is a JSON string from a closed vocabulary or a bounded opaque identifier;
JSON numbers, booleans, `null`, arrays, and nested objects are prohibited in records;
absent-but-required keys are invalid (`invalid_missing_required`); unknown facts use
the explicit sentinel strings (`unknown`, `indeterminate`, `not_scored`, `none`) —
never `null`, never omission.

## 6. Recommendation category classes (resolves P2-2)

The eight `recommendation_category` values partition exactly as follows. The partition
is normative and closed; a future category addition requires assignment to exactly one
class in the same change.

| Class | Categories |
|---|---|
| **allow-like** | `allow_simulation_only` |
| **observe-only** | `continue_read_only_observation` |
| **deny-like** | `deny` |
| **indeterminate-class** (escalation/abstention) | `request_human_approval`, `request_additional_evidence`, `abstain_insufficient_information`, `escalate_policy_conflict`, `invalid_input` |

`observe-only` is deliberately distinct from `allow-like`: it permits nothing beyond
the already-certified v1 read-only observation posture. It is nevertheless a positive
"continue" signal, so the cross-field rules below treat it as impermissible whenever
any governance fact is failed, conflicted, or indeterminate — continuing as normal
must never conceal a governance defect.

## 7. Cross-field validity rules (amended; resolves P2-2, P3-2, P3-5)

Rules replace §6 of the reviewed design in full:

1. `event_ref` must resolve exactly once in the corpus declared by the run's
   `corpus_class` (§4.1). Within one certification run, at most one record per
   `event_ref`; a duplicate makes **all** records bearing that `event_ref` ineligible.
2. Authority tiers are totally ordered: `none < tier_0 < tier_1 < tier_2 < tier_3`.
   `unknown` is incomparable. `authority_decision=within_boundary` requires
   `authority_requested` and `authority_available` both known and
   `available >= requested`. If either side is `unknown`, `authority_decision` must be
   `indeterminate`. If `authority_requested=none`, `authority_decision` must be
   `not_applicable`.
3. `authority_decision` in `{approval_required, denied, indeterminate,
   evaluation_error}` requires `recommendation_category` in the deny-like or
   indeterminate-class partitions. Allow-like and observe-only are both prohibited
   (this closes the reviewed design's gap where `continue_read_only_observation`
   could coexist with denied authority).
4. `policy_conflict_indicator=conflict` requires `policy_evaluation_result` in
   `{indeterminate, deny}` and prohibits allow-like and observe-only recommendations.
   `policy_conflict_indicator=unknown` prohibits allow-like recommendations.
5. `contract_resolution_status` not in `{resolved, not_applicable}` prohibits
   allow-like and observe-only recommendations.
6. `evidence_sufficiency` in `{insufficient, indeterminate, evidence_invalid}`
   prohibits allow-like and observe-only recommendations.
7. `schema_validation_status` other than `valid` requires `recommendation_category`
   in `{invalid_input, abstain_insufficient_information}`.
8. `uncertainty_reason=none` requires all factual evaluations determinate,
   `schema_validation_status=valid`, and `confidence_bucket` scored.
9. `confidence_bucket=not_scored` if and only if `uncertainty_reason=not_scored`.
10. Unknown/indeterminate values remain admissible for observation but make the record
    ineligible for a definitive correctness label unless the recommendation is an
    appropriate deny-like or indeterminate-class outcome.
11. Embedded values of fields 12, 15, 16, 17, and 18 are producer/assembler claims.
    Consumers must recompute each of them per `design/record_assembly_order.md`;
    any mismatch fails closed. No field in this record conveys executable permission.

## 8. Source independence and anti-circularity (unchanged, restated)

Fields 3–11 must be produced or attested by sources independent of Olympus
recommendation generation; field 12 by the independent validator; fields 13–15 by
Olympus only after fields 1–12 and field 17 are frozen; field 18 by the independent
assembler at advisory freeze; field 16 by the independent assembler at run close.
If the only available source for a factual field is Olympus itself, that field is
`indeterminate` and the event cannot establish recommendation correctness. Ground
truth remains the separate blinded human adjudication artifact
(`design/human_adjudication_store.md`); human labels are never exported from Hermes
and never enter Olympus inputs.

## 9. P3 dispositions not covered above

- **Schema-validation anchoring (P3-3):** accepted risk with rationale. A stage-A
  reviewer who sees `schema_validation_status != valid` can infer the recommendation
  class, but for invalid-payload cases the correct recommendation is fixed by rule 7,
  so the adjudication rubric for those cases scores rule conformance, not independent
  judgment; anchoring is immaterial there. Documented in
  `design/human_adjudication_store.md`.
- **Sparse-corpus aggregation (P3-6):** the k>=5 minimum-cell rule is retained as a
  floor. New rule: if suppression would remove more than 20 percent of events from a
  published aggregate, the publisher must coarsen the reporting taxonomy (merge
  classes) rather than lower k. The adequacy of k=5 remains an explicit privacy-gate
  question (open question 12) and is non-blocking for design review.
- **Historical v1 certification claims (P3-7):** every statement in this package that
  describes the v1 stream as "certified" is an inherited claim from the source
  workspace, not a fact this package establishes. Before any Phase 3 or later gate,
  the v1 certification record and stream digest must be independently re-attested in
  the repository. R2's design validity does not depend on those claims.
